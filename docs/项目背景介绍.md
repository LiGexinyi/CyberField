# CyberField · 项目背景介绍

> 用途：把本文件发给任意 AI 助手，即可获得讨论「后续数据处理 / 分析」所需的完整上下文。
> 更新日期：2026-11-08

## 一、项目是什么

一个面向互联网「热梗 / 话题」研究的**多源采集 + 可视化分析平台**，单人本地开发，
三周冲刺（2026-11-07 → 11-28）内从采集打通做到 Web 仪表盘。研究目标示例：
某热梗（如「奶龙」「小猫」）在 B站 / 微博 / 豆瓣上是**怎么火起来的、谁在讨论、
话题如何演变、各方什么态度**。

### 三周计划（详见 docs/roadmap.md）
- **第 1 周（11-07 → 11-13）**：打通简单合规的采集源 ✅ 已基本完成
- **第 2 周（11-14 → 11-20）**：六大分析引擎（REST API）
- **第 3 周（11-21 → 11-27）**：FastAPI + ECharts Web 可视化 + 用户系统整合

### 已规划的六大分析
1. **时间线梗演化**：按天关键词词频 → 平滑曲线 + 热度峰值标注
2. **使用群体画像**：平台 / 作者 / 关键词分布 + 聚类
3. **话题共现网络**：关键词共现矩阵 → 网络结构图
4. **讨论度**：各平台 / 各关键词的热度对比
5. **态度分析**：中文预训练情感模型（HuggingFace roberta），正面 / 负面 / 中性分布
6. **LLM 深度分析（预留）**：`LLMProvider` 抽象接口，后续接 Ollama / OpenAI 兼容 API，
   做梗演化叙事、态度提炼、趋势预测

## 二、当前技术状态

### 已接入的采集源（均为游客态，免登录）
| 源 | 适配器名 | 说明 |
|---|---|---|
| B站 | `bilibili_api` | 先访问主页拿游客 Cookie，再调公开搜索 API；返回标题 / UP主 / 时间 / 播放量 |
| 豆瓣 | `douban_api` | 移动端 rexxar 公开搜索接口（官方 API 已停）；书影音条目，作者取导演、时间取上映年份 |
| 微博 | `weibo_api` | 实现「访客激活流程」（genvisitor → incarnate 换发 SUB/SUBP Cookie）后搜索；返回正文 / 作者 / 时间 / 转发评论点赞 |

暂缓：知乎（游客态需签名，不可行）、小红书 / 抖音 / 快手 / 贴吧（需 MediaCrawler 扫码登录）。

### 代码结构
```
CyberField/
├── collect/
│   ├── post.py           统一数据契约 Post（所有源输出统一格式）
│   ├── orchestrator.py   多源调度：逐个调用、失败跳过、按 (platform,url) 去重
│   ├── store.py          采集库读写：SQLite data/collect.db
│   ├── demo_cli.py       终端交互 Demo（采集/浏览/统计/导出，支持分页）
│   └── sources/          B站 / 豆瓣 / 微博适配器 + HTTP 会话
├── data/
│   ├── collect.db        SQLite 采集库
│   └── export/           导出 CSV / JSON
├── docs/                 roadmap.md / code_overview.md / 本文件
└── README.md             开发日志
```

技术约束：**纯 Python 标准库**（HTTP 用 urllib 自封装，零第三方依赖）；单机 SQLite；
本地开发，无远程仓库，不 git push。

## 三、数据结构（讨论数据处理的核心）

统一契约 `Post`（dataclass）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `platform` | str | 规范化平台名：bilibili / weibo / douban / xiaohongshu ... |
| `title` | str | 标题 |
| `text` | str | 正文 / 摘要 |
| `url` | str | 原链接（与 platform 共同构成去重键） |
| `author` | str | 作者昵称（已脱敏） |
| `published_at` | str | 发布时间，尽量规范为 `YYYY-MM-DD HH:MM:SS` |
| `source_adapter` | str | 数据来自哪个适配器 |
| `keyword` | str | 由哪个搜索关键词采到 |
| `extra` | dict | 平台附加数据（如互动数），**当前未持久化入库** |

落库表 `collected_posts`（data/collect.db）：
```
id, keyword, platform, title, text, url, author,
published_at, source_adapter, fetched_at
UNIQUE(platform, url)   -- 幂等去重
索引：keyword / platform / published_at
```

### 数据现状（2026-11-08）
- 当前 **83 条真实数据**：B站 + 微博 + 豆瓣，来自若干关键词（奶龙 / 小猫 / 奥德赛等）
- 已清空过早期 18 条 MediaCrawler 模拟假数据，现存均为真实采集
- 字段质量差异：B站 / 微博较完整（作者、时间、正文齐）；豆瓣是书影音条目，
  **作者取导演**（card_subtitle 解析）、**时间取上映/首播年份**（year 字段）；
  部分条目导演为空属数据源本身缺失，时间列全部已补齐
- `extra`（互动数等）目前采集时有但**未写库**——讨论时值得考虑是否补存

### 采集与清洗模式（2026-11-08 新增）
- **浏览器模式（默认）**：`orchestrator.collect(..., save=False)` 搜索 → 清洗 →
  直接展示，**不入库、用完即弃**，就像浏览器浏览网页；
- **入库模式**：`save=True` 时清洗后才写 collect.db，原始中间数据不保留；
- **清洗（collect/cleaner.py）**：删空文本 → 按 (platform,url) 去重 → 时间升序
  排序（空时间排最后），纯标准库内存操作；
- **单次采集上限实测**：B站每页 20 条但**支持翻页**（limit 传 45 实返 41 条）；
  豆瓣同样用 start 偏移分页（limit 传 60 实返 60 条，页间延迟+need_login 降级）；
  微博游客态不稳定（时灵时不灵，单页 4~6 条且翻页被拒），需登录态突破。

## 五、当前正在思考的问题（希望 AI 一起讨论）

数据已经能采进来、查得到、导得出，接下来核心问题是：**这批数据怎么分析、怎么组织，
才能支撑六大分析 + 后期 LLM？**

具体待议点：
1. **数据清洗与增强**：正文清洗（HTML 实体 / 微博话题 #xx# / 转发符号）、
   是否需要补存 `extra` 互动数、作者去重 / 别名归并；
2. **分析字段扩展**：是否在库表加列（embedding 向量、情感分数、主题 id）还是
   建独立分析表 / 旁路缓存？
3. **话题分析的输入**：用什么当话题单元——关键词共现？BERTopic 直接聚全文？
   中文分词选型（jieba / 预训练 tokenizer）？
4. **时间线演化的粒度**：按天词频即可，还是需要平台分桶、滑动窗口平滑？
5. **情感模型**：先跑现成 roberta 中文情感模型打分，还是针对「梗 / 网络流行语」
   语料微调？
6. **可视化先行还是分析先行**：三周时间紧，六大分析是否做 MVP 版本（每个分析
   一个图 + 一个 API）再迭代？
7. **LLM 预留**：现阶段的表结构 / 分析结果要不要设计成对 LLM 友好的形式
   （如分析结果 JSON 化、缓存）？

## 六、讨论时请 AI 注意的约束
- 本地单机、Python 标准库优先，尽量少引重型依赖；
- 数据量目前很小（百条级），不必为千万级设计，但结构要可扩展；
- 用户将自备平台账号登录（MediaCrawler 扫码），采集源会逐步扩；
- 所有分析结果应可导出（JSON / CSV），并最终上 Web 仪表盘。
